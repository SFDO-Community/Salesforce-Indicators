# Designing a Salesforce Indicator

An indicator configuration is four kinds of Custom Metadata Type record (bundle, item, bundle item, extension) that all have to agree with each other to work. Part of what makes this hard for users is that the data model supports building these records in almost any order — bundle first, item first, extensions added later, all valid — so there's no single mandated sequence to fall back on. The working assumption behind this skill (not a settled fact, just the pattern worth designing around) is that users who start from a field they already have in mind ("I have a Status field, let me make an item for it") tend to discover the bundle/action/extension questions later, after they've already committed to an appearance — which is more rework than starting from the purpose first.

This skill inverts that: start from the *purpose* — what should someone glancing at the record instantly understand — and let that purpose determine the object structure, not the other way around. Work through the interview below before generating anything. It's fine to loop back and revise earlier answers as later questions surface new requirements; that's normal, not a sign something went wrong.

Read `references/cmdt-schema.md` before or during the interview — it has the authoritative field list, picklist values, and five active validation rules (spanning `Indicator_Item__mdt`, `Indicator_Item_Extension__mdt`, and `Indicator_Bundle_Item__mdt`) worth checking the design against as you go, rather than discovering them at deploy time.

## Part 1 — The design interview

Work through these in order. Keep a running plain-language summary as you go (a short table works well) — you'll translate it directly into the JSON recipe in Part 2, and having it written down means the user can correct course before any file exists.

**How to ask, regardless of surface:** if an interactive structured-question tool is available, use it. If it isn't — a plain chat surface with no such widget — don't fall back to a long narrative the user has to comb through to find each question. Batch related questions together instead of asking one at a time, number them, and for each one give a short list of concrete options with a recommended default called out, so the user can reply tersely ("1b, 2 default, 3 skip") instead of writing prose or re-reading paragraphs to find what's actually being asked. Several of the steps below list options in this style specifically so they translate directly into that format.

### 1. What's the glance-value?

Ask what the person looking at the record page should instantly know, and why it matters to them — not what field holds the answer. "Is this account at risk of churning" is a purpose; "show the Health_Score__c field" is a field. The purpose determines everything downstream: how many indicators are needed, whether they need conditional treatment, and whether they need to be actionable. If the user opens with a field name, ask what decision or action that field is meant to inform — you may find the real answer needs a different or additional field once the purpose is clear.

### 2. Which object, and does this belong to an existing card or a new one?

Every bundle lives on exactly one object's record page. If the user already has a bundle on that object (ask, or check `force-app`/their org), find out whether this new indicator belongs alongside those existing ones or genuinely needs its own card — a new `Card_Title__c` and icon. Multiple small single-purpose cards are often easier for admins to maintain than one sprawling card; don't default to cramming everything into one bundle just because it's the same object.

If there's no natural card grouping at all (a one-off indicator with no peers), it can technically skip having a bundle relationship entirely — it'll just surface to the user as an "Unbundled Item" on the Indicator Setup tab. Confirm that's really wanted; usually a card home appears once there are 2+ related indicators.

Also worth raising here: a bundle doesn't have to be placed on the same object it reads from. The component's `mappedField` App Builder property lets a bundle built for one object (say, Account) be dropped onto a *related* object's page (say, Contact) by pointing it at the relationship field (`AccountId`) that leads there. If the user is about to build a near-duplicate of an existing bundle just to get it onto a different-but-related page, ask whether recycling the existing bundle this way would serve just as well instead. And since a page can host more than one bundle at once (different cards for different groupings, or the same page showing different bundles to different audiences via visibility rules), "does this belong on an existing card" isn't an either/or with "does it need its own card" — both can coexist on one page. Either way, encourage filling in each record's `Description__c` (internal-only, never shown to end users) with *why* it exists — cheap now, and the only thing that tells a future admin (or agent) what a given bundle/item/extension is for.

### 3. For each indicator: where does the value come from?

First check whether the purpose from Step 1 is actually a **single value** or a **compound/derived condition** — this is the question that most affects whether the rest of the design is buildable as stated, so settle it before anything else. Purposes phrased as "at risk," "overdue," "needs attention," or anything combining two independent signals ("this deal is stalled *and* the amount is large") are usually derived, not a single field. An item can only key off one field or one relationship path (a *single* date field's proximity to today is fully supported, see Step 5 — it's combining that with something else that's the problem). If the purpose genuinely combines two or more signals:
- The combining logic needs to live in a **formula field** (or a flow/process-updated field) on the object, created ahead of time in Setup → Object Manager — outside CMDT entirely, and outside what any command in this skill can create. Tell the user this explicitly as a concrete first step, not a footnote: they (or their admin) need that field to exist before an item can point at it.
- The team is exploring a partnership with a tool called Record Health Check that may handle some of these compound conditions more directly — not yet validated, so don't reference it as an available option until that's confirmed.

Once the value is confirmed to be a single field (whether that's a raw field or a formula field built for this purpose), two sources lead to different CMDT fields:
- **A direct field on the bundle's object** → `Field__c`, the bare API name.
- **A field on a related record** (up to 5 relationship hops away) → `Advanced_Field__c` plus `Advanced_Field_Label__c` for a human label.

Leaving both blank `Field__c` and `Advanced_Field__c` is never an option.

Ask which one applies before asking about icons or colors — it changes what "the value" even means for the rest of the interview.

### 4. What does it look like, and does "has any value" need its own appearance?

Get the default appearance: icon, optional short static text (badges truncate to ~3 characters or one emoji — don't let the user plan on a word fitting), hover text, colors. Check any proposed icon name against `assets/slds-icons-reference.csv` before writing it anywhere — an invalid icon name deploys without error and just silently shows nothing, so don't guess at a plausible-sounding one (e.g. don't assume every noun has a matching `standard:` icon just because it sounds right). When suggesting an icon, offer the user a short list of 2-4 real candidates from the reference file rather than either picking one unilaterally or deferring the whole decision to "customize it yourself later" — the user should get to choose among genuinely valid options at design time, not discover after deploy that the icon you picked doesn't exist, or be left to hunt for one themselves with no starting point. The same goes for `Image__c` (a URL instead of an icon) — ask which the user actually wants rather than assuming icon by default.

Reach for icon categories in this order, deliberately, rather than defaulting to whatever the reference file happens to list first:
1. **`standard:` and `custom:` icons first** — these are the icons designed to carry a colored backdrop, so they read clearly as indicators and `Icon_Background__c`/`Icon_Foreground__c` both work as expected on them.
2. **An emoji in `Static_Text__c`, when no icon in the reference file is a good conceptual match** — this produced genuinely good results in testing and is worth leaning into rather than forcing a mediocre icon match. Don't reach for this first, but don't be shy about it once standard/custom comes up empty.
3. **`utility:` icons next**, if neither of the above fits — but only propose a foreground color for these, per the background-color caveat in `references/cmdt-schema.md`. Don't propose an `Icon_Background__c` value for a utility icon.
4. **`doctype:` and `action:` icons only if the user specifically asks for one by name** — they render poorly in this package's base components, so don't suggest them as candidates on your own initiative.

If the design leaves `Static_Text__c` blank (icon-only, no glyph text), `Empty_Static_Text_Behavior__c` has to be set explicitly in the CSV — a validation rule enforces this, and the field's "Use Icon Only" default only applies in the Setup UI, not to a blank CSV cell. See `references/cmdt-schema.md`'s validation-rules section.

Then ask specifically: *when this value is missing, false, or zero, should it look meaningfully different from when it "has any value" — or should absence/false just render plainly like anything else?* This is `Show_False_or_Blank__c` and its mirrored `Inverse_*` fields. It's easy to skip past, but it's the difference between "this checkbox is unchecked, shown plainly" and "this checkbox is unchecked, which is actually the good/expected state, shown with a distinct green check." If the field is numeric, also ask whether `0` should count as blank for this purpose (`Zero_Behavior__c`).

This step is genuinely optional, in two different ways worth being explicit about: a user may skip it entirely because every value (present or absent) should render the same way, or a user may want to configure *only* the absent/false case and not the default — an indicator that's silent when there's nothing to flag and only appears when a value is missing or zero. Don't assume a "has any value" appearance is always wanted just because a field has one. It's also fine to skip this step and Step 5 (extensions, "has a specific value") both, and go straight from a bare field to a click action with no conditional appearance at all — not every indicator needs to change its look based on the data.

### 5. Does the appearance change based on a specific value? (Extensions)

If different values should render differently — a Stage picklist where "Closed Won" gets a trophy and "Closed Lost" gets a different color, a number where under/over a threshold matters, or a single date field's proximity to today (overdue, due soon, etc. — fully supported, see below) — that's one `Indicator_Item_Extension__mdt` record per distinct rule ("has a specific value"), attached to this item. Get concrete: exact strings to match (and whether it's equals/contains/starts-with), exact min/max numeric bounds (a min-only or max-only rule still needs `Minimum__c` set — see `references/cmdt-schema.md`'s requiredness notes), or a relative/definite date expression with a date-specific operator — and which rule should win if a value could match more than one (`Priority__c`, lower wins) — unless the field is a multi-select picklist where several extensions should show at once (`Display_Multiple__c` on the item).

If Step 3 already routed a compound condition to a formula field, the extension (if any) matches on that formula field's output, not on the raw underlying data — but a plain date field on its own doesn't need that detour; date-range extensions work directly against a date/datetime item.

### 6. Should clicking it do anything?

Not every indicator needs to be clickable. If it does: a **URL** (external link, or a Salesforce page — supports `{!Field_API_Name}` merge tokens) or a **Flow Modal** (runs a Screen Flow in a popup, refreshing the record on finish). Also ask: should the indicator itself be clickable, or should the action only fire from an explicit button in the hover popover (`Action_Confirm_Required__c`) — useful for actions with real consequences that shouldn't trigger from an accidental tap. This lives on the *bundle item* (the join), not the item itself, because the same item could have a different action (or none) in a different bundle — worth naming that trade-off to the user rather than treating it as a given: it means the false/blank-appearance toggle for the action (`Show_False_or_Blank_Action__c`) is also bundle-item-scoped, not something that follows the item itself or lives per-extension.

`{!Field_API_Name}` merge tokens work in more than just the action target — see `references/cmdt-schema.md`'s merge-token list for the full set (bundle card text, item hover text, extension hover text overrides, and action target). They do not work in the action button label or help text.

### 7. Where does it sit relative to its siblings?

If this item is joining an existing bundle, ask where it should appear — `Order__c` takes decimals, so slotting between two existing items (`1.5` between `1` and `2`) avoids renumbering the whole card.

## Part 2 — Generating the files

Once the interview settles, first assemble the design as a **JSON recipe** — see `references/json-recipe-schema.md` for the exact shape (`bundle` object, `items[]`, each item's nested `bundleItem` and `extensions[]`). This is the primary artifact of the interview: a single file capturing every field value decided in Part 1, structured the same way whether this design is a full bundle or a standalone item. Show it to the user before generating anything else — it's much cheaper to fix a wrong extension boundary here than after it's baked into CSV/XML. While assembling it, sanity-check the length of any compound `MasterLabel` value (bundle items and extensions especially, since their names are naturally built from two other names) against the 40-character DeveloperName limit — see `references/generation-workflow.md` for why this has to be caught here rather than at deploy time.

Ask where the user wants the JSON/CSV/XML files saved before generating anything — a real location in their project, not a scratch/temp directory by default (see `references/generation-workflow.md`). Someone iterating on a design wants to be able to come back to these files — and the JSON recipe in particular is also the file to hand to another admin, or post to a recipe library, if this design is meant to be shared, so it's worth keeping even after the CSVs/XML are generated and deployed.

CSV generation is then a mechanical transform *from* the JSON recipe, not a separate drafting pass — walk `bundle`/`items[]`/`extensions[]` and emit one row per record into the appropriate CSV. Then ask how the user wants to get it into an org: a **CSV import** via Salesforce Inspector Reloaded (no CLI needed — Workbench does *not* support this; its CMDT route is a manual metadata-zip deploy, not a CSV import), or **CLI deploy** via `sf cmdt generate records` + `sf project deploy start` (one command deploys everything, no per-record clicking). Read `references/generation-workflow.md` for exactly how each path works — it covers the CSV column conventions (including easy mistakes around bare field names, CSV comma-quoting, and the DeveloperName-sanitization rules) and the verified `sf cmdt generate records` invocation, including why it needs `assets/objects-reference/` (a customer with just the package installed doesn't have the CMDT field definitions locally, which that command needs to know each column's type). The CLI generation path has been run end to end and verified; the CSV-import path (Inspector Reloaded) has not — the CSV shape follows Inspector's documented column requirements, but treat that path as unverified until it's actually been exercised, and say so if the user asks.

Always build the CSVs first regardless of which path is chosen — CSV is both a valid end state and the required input to the CLI conversion. The JSON recipe stays the source of truth behind them; regenerate CSVs from it rather than hand-editing a CSV directly if something needs to change.

Before running any deploy command against a real org, show the user the generated file contents and confirm — CMDT deploys are easy to correct after the fact, but the user should still see what's about to land before it lands.

(If this is actually the package's own source repo rather than a customer's org — building sample/training config, not helping a customer configure their installed package — use `design-indicator-samples` instead, which handles the unprefixed field names and CumulusCI deploy convention that context needs.)
